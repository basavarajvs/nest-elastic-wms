# Document 7: Outbound - Shipping (Trailer Loading & Dispatch)

**Context:** Packed shipping cartons or palletized orders are moved to the shipping dock. The loader uses the RF device to load the trailer and seal it for departure.

### Sequence of Events
1. **Scan Dock Door:** Operator scans the outbound dock door barcode to initialize the loading session.
2. **Scan Trailer ID:** Operator scans the physical Trailer ID or OBLN (Order Bill of Lading Number).
3. **Scan Shipping LPN:** Operator scans each Shipping LPN (Carton or Pallet SSCC-18 label) as it is physically placed onto the truck.
4. **System Validation:** System verifies the scanned LPN belongs to the route/carrier assigned to this specific trailer. If an LPN belongs to a different truck, the RF alarms (Wrong Truck).
5. **Load Verification:** Operator views the "Load Progress" (e.g., 45/50 cartons loaded).
6. **Close Trailer:** Once the truck is full, the operator selects `Close Trailer` and enters the physical Seal Number (e.g., metal bolt seal).

### API & Backend Interactions
| Component | Details |
| :--- | :--- |
| **Logical API Call** | `POST /api/mobile/shipping/loading/scan` <br> `POST /api/mobile/shipping/trailers/{trailer_id}/close` |
| **Expected API Response** | Returns `validation_status` (Success/Alarm). On close, returns confirmation and updates manifest. |
| **Next Screen Prompt** | "Scan Next LPN" OR "Trailer Closed - Print Manifest" |
| **Backend Entities Updated** | **`trlr` (Trailer):** Updates status and records seal number. <br> **`lpn`:** Shipping LPNs are linked to the Trailer ID. <br> **`ord_hdr`:** Final status update to `SHIPPED` (or `LOAD_PND` until dispatch). <br> **`stop`:** Updates the route stop as loaded. |
| **Data Status Changes** | Trailer Status: `OPEN` → `CLOSED` / `SEALED`. <br> LPN Status: `PACKED` → `LOADED` → `SHIPPED`. <br> Order Status: `PACKED` → `SHIPPED`. |

---

### Summary of Core Manhattan RF Principles Demonstrated:
1. **Scan-Confirm-Execute:** The RF user almost never types an LPN or Location manually; they *must* scan a barcode. The system uses **Check Digits** on location barcodes to prevent scanning the wrong rack.
2. **Exception-Driven UI:** The RF screen only prompts for data entry when there is an exception (e.g., a short pick, a damaged item, or a blind cycle count). Standard flows are 1-touch confirmations.
3. **Task Interleaving:** Notice how in Putaway, Picking, and Cycle Count, the operator doesn't search for work; they press `Get Next Task`. The Manhattan Task Management engine dynamically queues work based on user proximity, equipment type, and priority.

In Manhattan WMS, once a truck arrives at the dock, the **receiving operator** takes over. The system expects the goods based on an ASN (Advance Ship Notice) or Purchase Order (PO). 

The receiver's job is to:

* Verify the trailer and dock door
* Scan the ASN/PO barcode
* Scan items and verify quantities
* Generate LPNs (License Plate Numbers) for pallets/cartons
* Apply LPN labels
* Move inventory to a staging location
